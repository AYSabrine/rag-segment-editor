# Final step — Production integration with Oracle (plan)

> **Status: planned, not implemented in this repository.**
> This portfolio version stores the rules in local files. In production, the
> final step connects the app to the Oracle database that drives the offers.
> This document explains *how*; the integration itself is done by the author in
> the target environment. **No Oracle code, connection string, credential, real
> table name or real schema is part of this project** — all names below are
> fictional.

---

## 1. The end-to-end flow

```
Business user (browser)
   │  "make the Regular Nudge segment more aggressive"
   ▼
Streamlit app  ── RAG proposes a change (JSON)
   │             ── validation (10 guardrails)
   │             ── impact simulation on the subscriber base
   │             ── impact check (overlap → rejected, no segment → warning)
   ▼  only an APPROVED change goes further
Oracle STAGING table      RULE_CHANGE_REQUESTS     (one row per approved change)
   ▼  apply procedure (PL/SQL), in ONE transaction
Oracle CONFIG table       NBO_SEGMENT_RULES        (the rule grid)
   │  + snapshot           NBO_RULES_VERSIONS      (every version of the grid)
   ▼
Daily NBO batch reads NBO_SEGMENT_RULES → assigns each subscriber a segment
   ▼
Next Best Offer per subscriber (offer intensity) → campaigns
```

The business changes the rules **in the app**; the change lands in Oracle; the
next NBO run uses the new grid, so **the offers change without a developer or a
release**.

## 2. Why a staging table, and not a direct write

| Direct write from the app | Staging table + apply procedure |
|---|---|
| The app needs write rights on the production grid | The app can only **insert requests**; it never touches the grid |
| A bug in the app can corrupt the offers | The database **re-checks** every request before applying it |
| Hard to coordinate with the daily batch | The procedure applies changes **between batch runs** |
| Rollback depends on the app | Every version is kept **in Oracle**; rollback is one procedure call |

The principle of the whole project stays the same down to the database:
**the AI proposes, deterministic controls verify, then the change is applied.**

## 3. Tables (fictional names)

**`RULE_CHANGE_REQUESTS`** — staging, written by the app
| Column | Content |
|---|---|
| `CHANGE_ID` | unique id generated by the app (e.g. `CHG-20261006-120325-2880`) |
| `REQUESTED_AT`, `REQUESTED_BY` | timestamp, user e-mail |
| `REQUEST_TEXT` | the exact sentence typed by the business |
| `SEGMENT_ID`, `FIELD_NAME`, `OLD_VALUE`, `NEW_VALUE` | the structured change |
| `BASE_VERSION` | version of the grid the simulation was run on |
| `IMPACT_OFFER_CHANGED`, `IMPACT_MOVED`, `IMPACT_UNASSIGNED` | simulated impact |
| `STATUS` | `PENDING` → `APPLIED` or `REJECTED` |
| `STATUS_REASON`, `APPLIED_AT`, `NEW_VERSION` | outcome of the apply procedure |

**`NBO_SEGMENT_RULES`** — the rule grid read by the NBO batch
(same columns as `data/segment_rules.csv`: bounds, roaming rule, risk combos,
offer intensity, active flag) plus `VERSION_NO`.

**`NBO_RULES_VERSIONS`** — one full snapshot of the grid per applied change
(`VERSION_NO`, `CHANGE_ID`, `CREATED_AT`, snapshot of every rule row).

## 4. The apply procedure (PL/SQL), step by step

For each `PENDING` request, in **one transaction**:

1. **Lock the grid** so that two changes cannot be applied at the same time.
2. **Version check** — if `BASE_VERSION` ≠ current version, the grid changed
   since the simulation → `REJECTED` ("rules changed meanwhile, re-simulate").
3. **Re-run the guardrails in the database** — allowed values, integer bounds,
   `MIN < MAX`, risk-combination format, no unknown segment or field.
4. **Overlap check in SQL** — on the would-be grid, no subscriber profile may
   match two active segments (same rule as the app's impact check).
5. **Apply** — update the rule row, increment `VERSION_NO`, insert the snapshot
   in `NBO_RULES_VERSIONS`, set the request to `APPLIED`.
6. **Any failure → rollback** of the whole transaction and `REJECTED` with the
   reason. The grid is never left half-updated.

**Rollback of a business decision** = re-apply a previous snapshot from
`NBO_RULES_VERSIONS` through the same procedure (so it is traced too).

## 5. Security

- The app connects with a **dedicated technical account** that can only
  `INSERT` into `RULE_CHANGE_REQUESTS` and read the grid. It has **no update
  right** on `NBO_SEGMENT_RULES`.
- Only the apply procedure (owned by the schema owner) can modify the grid.
- Connection details live in environment variables / a secret vault, **never in
  the code or the repository** — same rule as the OpenAI key today (`.env`).
- With real customer data, the LLM must run inside the company perimeter
  (e.g. a private Azure OpenAI deployment or a local model) — the architecture is
  provider-agnostic, only the model connector changes.

## 6. From this repository to production

| Today (portfolio, local files) | Production (Oracle) |
|---|---|
| `data/segment_rules.csv` | `NBO_SEGMENT_RULES` |
| `data/audit/rules_versions/*_before.csv / _after.csv` | `NBO_RULES_VERSIONS` |
| `data/audit/change_log.jsonl` | `RULE_CHANGE_REQUESTS` (+ its status history) |
| `save_rules()` in `rag/engine.py` | insert of an approved request into the staging table |
| pandas matching in `assign_segments()` | the daily NBO batch (SQL / PL/SQL) |

Only the storage step changes: the RAG editor, the guardrails, the impact
simulation and the audit trail are reused as they are.
